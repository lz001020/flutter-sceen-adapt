# 项目路线图

## 产品定位

`screen_adapt` 面向 **Android / iOS 移动端、单窗口 Flutter 应用**。

核心目标是把设计稿尺寸映射到 Flutter 的全局逻辑坐标系，让业务页面直接使用设计稿尺寸完成布局，同时保持布局、`MediaQuery`、字体、键盘 inset 和指针事件的一致性。

项目当前不以支持所有平台和所有布局模型为目标：

- 不支持 Flutter Web、桌面端和多窗口 / 多 view；
- 不把 `.w / .h / .sp` 扩展方法作为核心 API；
- 不默认要求业务页面使用局部反适配；
- 不为理论上的未来平台预先增加抽象层。

## 设计原则

1. **全局适配是主路径。** 普通页面、列表、弹窗和 Flutter 组件都应直接使用统一设计稿坐标。
2. **例外能力是扩展。** 只有确实需要设备原始逻辑尺寸的区域，才引入局部反适配或原生视图补偿。
3. **核心链路保持短。** 纯计算、状态控制、Flutter binding 和 Scope 各自负责一件事，避免为未来平台预建抽象。
4. **行为先于 API 数量。** 新增能力必须对应真实业务场景、可复现问题和测试证据。
5. **移动端单窗口优先验证。** 文档、示例、性能和兼容结论都以当前支持范围为准。

## 路线图

### 阶段 0：范围和契约冻结

目标：先把项目边界写清楚，避免核心库继续被例外场景牵引。

- 固定 Android / iOS、单窗口支持范围；
- 固定设计稿尺寸、适配策略、字体和 `MediaQuery` 的行为契约；
- 明确 `AdaptController`、binding、Scope 的职责和生命周期；
- 将 `UnscaledZone`、`AdaptedPlatformView`、`PhysicalPixelZone` 标记为扩展能力；
- 在文档中区分“核心保证”和“已知限制”。

完成标准：新功能可以回答“它属于核心链路还是扩展模块”，且不会因为增加一个例外场景修改全局适配公式。

### 阶段 1：核心适配稳定化

目标：把全局适配做成可靠、可测试、可维护的主产品。

- 纯计算层：设计稿到设备坐标、字体策略和 `MediaQuery` 转换；
- Controller：配置、设备快照、启停、幂等通知；
- binding：设备指标、`ViewConfiguration`、指针坐标转换；
- Scope：向 Flutter 子树发布一致的指标和 `MediaQuery`；
- 覆盖旋转、键盘 `viewInsets`、系统字体、无效 DPR、设计稿切换和禁用适配；
- 收紧公共导出，避免业务依赖内部兼容状态。

完成标准：核心测试和 example 测试稳定通过，普通业务页面不需要任何局部反适配组件即可完成适配。

### 阶段 2：核心性能和开发体验

目标：让全局适配适合长期用于真实项目。

- 测量配置更新、父级重建、列表滚动和指针转换的开销；
- 消除重复计算和重复通知；
- 提供初始化、配置切换、调试诊断和常见错误的清晰文档；
- 保持 API 数量小，优先改进错误信息和迁移说明；
- 建立移动端真机或模拟器的回归清单。

完成标准：性能数据有明确测试条件，文档能覆盖从接入到排错的完整路径。

### 阶段 3：按需引入扩展模块

目标：只为已经确认的业务需求增加例外能力。

扩展模块不改变核心坐标计算，也不默认进入普通页面：

- `UnscaledZone`：用于旧页面迁移、固定原始逻辑尺寸的局部控件和明确的原生尺寸区域；
- `AdaptedPlatformView`：只处理已验证的 PlatformView / WebView / 地图等嵌入场景；
- `PhysicalPixelZone`：只处理像素精度绘制，不承担通用布局适配；
- `LegacyScreenUtilScope`：作为迁移工具，而不是新页面的推荐写法。

每个扩展必须同时具备：真实用例、边界说明、独立测试、示例页面和失败时的降级行为。没有实际使用方时，不继续扩大其 API。

### 阶段 4：发布和兼容治理

目标：形成可持续发布的移动端库。

- 清理临时 shim 和未承诺的旧入口；
- 发布前执行分析、测试、打包内容检查和 `flutter pub publish --dry-run`；
- 维护变更日志、迁移指南和已知限制；
- 对破坏性变更使用明确的主版本策略；
- 不因为发布压力承诺 Web、桌面或多窗口支持。

## 暂不规划

以下内容不进入当前版本路线图，除非项目定位发生变化并重新评估：

- Flutter Web、桌面端、多窗口和多 view；
- 通用响应式布局系统或断点系统；
- 为所有第三方组件提供自动兼容层；
- 将局部反适配能力做成页面默认使用方式；
- 为尚无真实需求的平台或渲染后端预建抽象。

## 需求进入规则

新增需求至少需要说明：

1. 真实业务场景和当前核心能力为什么无法解决；
2. 是否可以作为扩展模块，不改变核心适配链路；
3. 对布局、绘制、命中测试、字体和 `MediaQuery` 的影响；
4. 测试和文档如何证明它在移动端单窗口范围内可用；
5. 如果长期没有第二个使用场景，是否应保持为内部实现而不是公共 API。
