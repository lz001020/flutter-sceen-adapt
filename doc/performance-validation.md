# 性能验证

已测场景中，两库优化后的帧耗时接近，逐轮快慢存在变化；静态子树复用在复杂页面上能降低构建成本。vivo 快速滚动存在重复的 raster 长帧波动，原因尚未定位，因此跨设备性能稳定性仍待验证。

本页保留关键数据与复现方法。历史采样来自迁移前性能宿主；当前代码统一在 `demo/`，迁移后尚未重跑设备性能采样。完整逐轮报告与原始日志已本地归档。

## 复杂图文父级更新

`complexParentRebuild` 测量复杂静态子树的父级更新成本。它使用 12 张本地混合图文卡片，覆盖多图、富文本、多行布局、标签、阴影、裁剪、图表和可变高度内容；图片在测量前预缓存。12 张卡片在单个滚动容器中全部挂载，是刻意放大的静态树压力场景，不能代表虚拟化长列表的每帧工作量。对齐测试用 DPR 3.0 与 3.2 模拟相同物理空间，观察到的物理边缘最大差约 1.8px，以 2px 为验收容差；误差原因未进一步归因。三轮 × 四写法共 2160 帧，均无超过 16.667ms 的帧，方向为 rotation 0，设备设置恢复成功。

| 写法 | 复杂卡片 build | UI p90 | raster p90 | total p90 | total p99 |
| --- | ---: | ---: | ---: | ---: | ---: |
| designConst | 0 | 0.887 | 2.205 | 4.262 | 5.456 |
| designDynamic | 2160 | 2.265 | 1.766 | 5.023 | 5.835 |
| screenUtilOptimized | 0 | 0.896 | 2.274 | 4.467 | 5.578 |
| screenUtilInline | 2160 | 2.475 | 1.789 | 5.287 | 6.545 |

相对各自动态写法，design_scale 的复杂卡片 build 从 2160 降到 0，UI p90 下降约 61%，total p90 下降约 15%；ScreenUtil 的对应下降约 64% 和 16%。这说明在复杂静态子树中，复用效果比八卡片基线更容易出现在 UI 帧数据里；复用机制是 Flutter 通用能力，不能归因于某一个适配库。

两库优化组的 total p90 中位数相差 0.205ms（design_scale 较低约 4.6%），但逐轮 design_scale 为 5.025 / 4.049 / 4.262ms，ScreenUtil 为 4.660 / 3.711 / 4.467ms：前两轮 ScreenUtil 较低，第三轮 design_scale 较低。不能把中位数写成稳定领先。两边同时增加 RepaintBoundary 的诊断批次中，design_scale 为 4.641ms、ScreenUtil 为 4.290ms，方向发生变化；两个批次的调度与 raster 差异不能相减为绘制隔离的确定收益。隔离批次不替代默认结果。

## 差异定位摘要

- 修正了对照页面的标题高度、边框缩放和字体参数。规则页面物理矩形容差为 1px，复杂页面为 2px；复杂页面最大观察差约 1.8px。
- 两库同时隔离静态区域绘制后，PAINT p90 从约 0.608–1.063ms 降至 0.179–0.274ms，支持重绘是 UI 耗时贡献之一。独立诊断批次不用于默认性能排名。
- 父级更新诊断只在启动时记录 3 次 view 配置，未观察到逐帧适配重算。剩余库间差异尚未完全归因。

## 场景与对照


三个更新专项先执行 30 次预热，再测量 180 次更新。前两个共用一个八商品卡片页面；第三个使用 12 张本地混合图文卡片。每次更新等待渲染帧完成；以相同更新工作量比较，不以固定墙钟时间比较。较慢实现可能花更长时间，不能把相同更新数误称相同吞吐率。

| 场景 | 固定工作量 | 要回答的问题 |
| --- | --- | --- |
| 父级重建 parentRebuild | 每次切换顶部标记，商品内容不变 | 不变子树的复用能省掉多少构建工作 |
| 局部更新 localUpdate | 每次只更新一张卡片价格，轮询八张卡片 | 静态详情是否随价格重复构建，以及正常状态隔离后的成本 |
| 复杂父级更新 complexParentRebuild | 每次切换复杂信息流顶部标记，12 张图文卡片不变 | 多图、富文本、标签、阴影、裁剪和图表组成的静态子树被复用后，UI/整帧差异是否放大 |
| 复杂信息流（保留原场景） | 轮播、展开与滚动，沿用原脚本 | 新 item 首次构建及完整页面的实际开销，不作为 const 收益的直接证明 |

| 实现 | 适配方式与组件策略 |
| --- | --- |
| designConst | design_scale；父级返回 const 商品/复杂信息流区域；局部更新通过 ValueListenableBuilder.child 复用静态详情 |
| designDynamic | design_scale；父级创建新商品/复杂信息流区域；局部更新重新创建静态详情 |
| screenUtilOptimized | ScreenUtil；父级返回 const 封装组件，在内部换算尺寸；局部更新同样复用 child |
| screenUtilInline | ScreenUtil；父级创建新商品/复杂信息流区域，局部更新重新创建详情；运行时换算尺寸 |

四组使用相同的 ValueNotifier 通知和状态管理粒度。ScreenUtil 在组件内复用尺寸倍率，静态区域依赖 MediaQuery.size 以响应窗口变化。复杂场景采用 `demo/assets/feed.png`，测量前预缓存图片；它测量已挂载静态树的父级更新，未覆盖首次解码、网络、内存或功耗。

## 采集与有效性

- 记录组件边界的 build 次数，以及 UI、raster、total 的 p90/p99 与超过 16.667ms 的帧数。UI 使用 FrameTiming.buildDuration，涵盖构建、布局与绘制命令生成；各项分位数不可相加。
- 每组独立进程，排除启动与 30 次预热，等待 FrameTiming 回调后收集 180 次更新。默认三轮，第二轮反转顺序，保留异常轮次。
- 工作量断言：规则父级优化组静态区域 0 次，动态组区域 180 次、详情 1440 次；复杂父级优化组 0 次，动态组区域 180 次、卡片 2160 次；局部各组价格 180 次，优化组详情 0 次、动态组 180 次。
- 帧数不足、计数或方向不符时判为采集失败。单轮用于工具验收；历史 const/inline 压力测试单独记录，不混入优化组的库间比较。

## 复现

在仓库根目录执行，需连接 Android 真机：

```sh
(cd demo && flutter pub get && flutter analyze && flutter test test/update_benchmark_test.dart)
python3 tool/run_portrait_performance.py <adb-device>
# 仅复杂图文更新：三轮、四种写法
python3 tool/run_portrait_performance.py <adb-device> --updates-only \
  --rounds 3 --scenarios complexParentRebuild
# 快速滚动复验
./tool/compare_fast_list_performance.sh <adb-device>
```

总控默认运行更新专项及三轮混合信息流。运行会替换 demo APK（与功能回归共用应用标识）并清空 logcat；总控临时关闭自动旋转、固定竖屏，逐组核对方向并在结束或失败时恢复旋转设置。不修改分辨率、密度、字号或刷新率。不要与功能回归同时运行。

更新报告位于 `build/update-benchmark-<时间>/`，包含配置、逐轮指标、计数、日志及首尾显示和温控快照；总控结果位于 `build/portrait-performance-<时间>/`。先核对工作量，再比较 UI、整帧与长尾。

需要定位绘制开销时另采集诊断批次：

```sh
python3 tool/run_portrait_performance.py <adb-device> --updates-only --diagnostics
python3 tool/run_portrait_performance.py <adb-device> --updates-only --diagnostics --isolate-paint
python3 tool/summarize_update_timeline.py build/update-benchmark-<时间>
```

Timeline 阶段可能嵌套并包含线程等待，不能相加为 CPU 时间；诊断开销和调度会影响结果，诊断批次单独分析。
