# 发布前性能复核与差异定位（2026-10-15）

## 结论

在小米 14 本轮锁定竖屏、对齐页面工作量的 Profile 测试中，两库帧耗时接近，design_scale 优化组的 total p90 中位数仍略高：父级更新高 0.167ms（约 3.4%），局部更新高 0.114ms（约 2.3%）。不能概括为本库“略有性能优势”。两场景共 24 组、4320 帧，均未超过固定 16.667ms 参考预算；这不是严格高刷验收，也不是性能等价检验。

已经找到对比实现中未对齐的布局参数，并验证了静态子树重绘对 UI 耗时的贡献。剩余库间耗时差异尚未完全归因：没有证据说明它来自逐帧适配计算，也没有受控的核心版本前后对照来确认版本回退。vivo 历史 raster 波动仍未关闭。

库的明确价值是按设计坐标书写布局、减少逐处尺寸换算。两库均能使用 Flutter 的 const 和 child 复用优化；是否减少开发工时，需要另做同页面实现与修改成本对照，不能由本次帧数据证明。

## 测试条件与通过标准

小米 14 / 23127PN0CC / SM8650 / Android 16，1200×2670 / 480dpi；Flutter 3.35.7、Dart 3.9.2、ScreenUtil 5.9.3。Profile 模式，两个更新场景、四种写法、三轮，第二轮反转执行顺序。每组预热 30 次、测量 180 次更新；逐组检查有效显示方向及构建次数。CPU/GPU 频率未固定，三轮中位数不构成统计显著性证明。

最终排名关闭 Timeline，保留默认绘制路径，没有加 RepaintBoundary。24 组工作量断言与帧数检查通过，48 份方向快照均为 rotation 0 / 1200×2670，原旋转设置恢复成功。UI 为 FrameTiming.buildDuration，包含布局及绘制命令生成；独立分位数不能相加。

## 新增复杂图文父级更新专项

为验证“页面复杂后重建成本更容易显现”，新增 `complexParentRebuild` 场景。它使用 12 张本地混合图文卡片，覆盖多图、富文本、多行布局、标签、阴影、裁剪、图表和可变高度内容；图片在测量前预缓存。12 张卡片在单个滚动容器中全部挂载，是刻意放大的静态树压力场景，不能代表虚拟化长列表的每帧工作量。对齐测试用 DPR 3.0 与 3.2 模拟相同物理空间，观察到的物理边缘最大差约 1.8px，以 2px 为验收容差；误差原因未进一步归因。三轮 × 四写法共 2160 帧，均无超过 16.667ms 的帧，方向为 rotation 0，设备设置恢复成功。

| 写法 | 复杂卡片 build | UI p90 | raster p90 | total p90 | total p99 |
| --- | ---: | ---: | ---: | ---: | ---: |
| designConst | 0 | 0.887 | 2.205 | 4.262 | 5.456 |
| designDynamic | 2160 | 2.265 | 1.766 | 5.023 | 5.835 |
| screenUtilOptimized | 0 | 0.896 | 2.274 | 4.467 | 5.578 |
| screenUtilInline | 2160 | 2.475 | 1.789 | 5.287 | 6.545 |

相对各自动态写法，design_scale 的复杂卡片 build 从 2160 降到 0，UI p90 下降约 61%，total p90 下降约 15%；ScreenUtil 的对应下降约 64% 和 16%。这说明在复杂静态子树中，复用效果比八卡片基线更容易出现在 UI 帧数据里；复用机制是 Flutter 通用能力，不能归因于某一个适配库。

两库优化组的 total p90 中位数相差 0.205ms（design_scale 较低约 4.6%），但逐轮 design_scale 为 5.025 / 4.049 / 4.262ms，ScreenUtil 为 4.660 / 3.711 / 4.467ms：前两轮 ScreenUtil 较低，第三轮 design_scale 较低。不能把中位数写成稳定领先。两边同时增加 RepaintBoundary 的诊断批次中，design_scale 为 4.641ms、ScreenUtil 为 4.290ms，方向发生变化；两个批次的调度与 raster 差异不能相减为绘制隔离的确定收益。隔离批次不替代默认结果。

主报告：`build/update-benchmark-20261015194853/`；同样工作负载的绘制隔离诊断：`build/update-benchmark-20261015205359/`；总控目录分别为 `build/portrait-performance-20261015194852/` 和 `build/portrait-performance-20261015205358/`。复现：

```sh
python3 tool/run_portrait_performance.py <adb-device> --updates-only \
  --rounds 3 --scenarios complexParentRebuild
```

该场景测量的是已缓存本地图片的父级更新，不包含网络、首次图片解码、内存、功耗或真实业务数据变化。

## 差异定位：发现、验证与未决项

1. **对比页面存在工作量偏差，已修正。** ScreenUtil 标题高度 32 和默认边框 1 曾未缩放，标题默认字体也未与 design_scale 对齐。现明确统一字体族、字号、行高、字距、字重、颜色，按倍率换算标题及边框。非单位倍率 Widget 测试核对物理矩形（误差不超过 1 个物理像素）和边框宽度，通过。尚未做字形栅格化逐像素验证。修正前后不同批次仍有调度差异，不能把全部耗时变化归因于布局修正。
2. **没有 rebuild 不表示没有重绘，已做诊断对照。** 原始绘制路径的 Timeline 中，纯 BUILD p90 约 0.088–0.138ms，PAINT p90 约 0.608–1.063ms。两库同时为静态商品区增加 RepaintBoundary 后，PAINT p90 降至 0.179–0.274ms。结果支持标题更新带动静态区域重绘是耗时贡献之一，不证明它解释全部库间差异。隔离仅为可选 benchmark 诊断，未写入库或默认排名。
3. **未观察到逐帧适配配置重算。** 原始路径诊断日志仅启动阶段 3 条 view_config，没有输入事件；Controller 由设备指标或配置变化触发通知。BUILD 差异很小且第三轮快慢反转，不支持将整段 UI 时间归为尺寸换算成本。
4. **生产日志已清理。** binding 的 view_config 和 pointer 日志只在 kDebugMode 下运行，profile/release 不再生成这些诊断字符串。该修改属于生产清理，不是父级测试差异的根因；该场景原本没有指针或逐帧配置日志。

Timeline 两批各六组、每组 180 帧，全部计数与方向检查通过。未隔离批次 UI p90 中位数为 1.619 / 1.455ms，隔离批次为 0.962 / 0.942ms。两个独立批次受调度影响，不能将差值解释成确定的算法成本。事件存在嵌套与线程间等待；GPU 绘制事件因测量边界截取为 179 条，不能将阶段分位数或总和相加成整帧 CPU 时间。GC 时间事件不等同分配量或内存占用测量。
