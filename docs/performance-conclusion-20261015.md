# 性能观测记录：方向未受控批次（2026-10-15）

最新受控竖屏结果见 [锁定竖屏复验](performance-conclusion-portrait-20261015.md)。下文保留原批次数据和判断历史，不替代新报告。

## 结论与适用范围

方向控制补充：核查完整显示快照后，开始时 `mOverrideDisplayInfo` 为 rotation 0 / 1200×2670，结束时为 rotation 1 / 2670×1200，即本批首尾逻辑方向不一致。design_scale 各专项日志中的倍率仍为 1.0667（DPR 3.2），但没有逐组方向快照和测量期间方向记录，无法确认方向变化发生在何时，也无法证明所有对照在相同方向采样。本批耗时数据降为方向未受控的观测记录，不作为性能回退或稳定库间差异的正式判据；构建计数验证仍保留。需固定方向并逐组记录有效视口后复验。

design_scale 的常量尺寸写法可以配合 Flutter 子树复用，避免无关业务更新触发静态区域重建。这项机制已在小米 14 三轮专项和 vivo 单轮工具验收中得到计数验证，但 ScreenUtil 的合理组件封装同样能做到，不能声称为 design_scale 独有的性能能力。

小米的两个更新专项中，design_scale 优化组的 UI / total p90 中位数均高于 ScreenUtil 优化组；当前证据不支持“比 ScreenUtil 普遍更快”。可确认的是组件复用生效，以及在本次固定工作量下的实际帧耗时。不能将测试完成等同于跨设备稳定性、高刷或正式业务收益验收。

### 能确认的构建收益

父级场景中，两库优化组的商品区域、卡片、静态详情、价格组件均为 0 次重建；动态组分别为 180 / 1440 / 1440 / 1440 次。0 次仅针对不变商品区域的指定组件边界，顶部标记仍正常更新，不表示整帧没有构建工作。

局部场景中，各组都完成 180 次价格组件构建；静态详情由动态组 180 次降为优化组 0 次，商品区域和卡片均为 0 次。两库使用相同 ValueNotifier 粒度和 child 复用方法，不能把状态隔离的收益归于适配库。

### 耗时如何解读

- design_scale 父级场景 const 相对自身动态写法，UI p90 中位数低约 38.1%，total p90 低约 22.3%。这是具体写法对照；第三轮没有重现耗时优势，不能宣传为稳定提升幅度。
- 两库优化组横向对比：父级场景 design_scale 的 UI / total p90 中位数高 0.182 / 0.426ms；局部场景高 0.068 / 0.267ms。父级场景三轮均为 ScreenUtil 优化组较低；局部 UI 差异方向随轮次变化。
- 局部场景中，ScreenUtil 动态组的 UI / total p90 中位数反而低于其优化组。减少静态详情 build 次数已被确认，但当前轻量子树下的帧耗时收益并不稳定；不能据此推导“不复用更好”。
- 三轮仅为小样本描述统计，未计算置信区间或执行显著性检验；不能把小差异推广为适配算法的固有成本或业务体验差异。

## 复杂信息流：本次三轮复验

沿用共享 1000 项、四类变高卡片的场景，包含富文本、图片、阴影、图表、轮播和展开动画。每轮执行 2 次横向滚动、5 次展开/收起、50 次纵向滚动（120ms、视口高度的 80%），第二轮交换库的运行顺序。6 次运行均确认 `mixedActions=7` 与 `automationComplete=50`，脚本正常退出；脚本本身不设置帧性能通过门槛。

本次 design_scale total p90 中位数高 0.445ms（相对 ScreenUtil 约 11.1%），三轮均较高；长帧计数仍很少但非零。帧数中位数相差约 0.6%，操作工作量相同，不保证逐帧画面完全相同。复杂信息流沿用累计帧统计，包括早期帧，与更新专项排除预热后的窗口不同，不能将两个场景的数值直接作横向排名。

2026-10-13 同场景历史中位数为 5.083 / 5.744ms，优势方向与本次相反。两批均保留，说明不能只挑有利批次宣称稳定领先。当前未控制系统调度、后台负载等所有变量，也未用 trace 分离适配机制的纯成本。

本次构建输出保存在 `build/update-benchmark-20261015000808/mixed-feed-run.log`，六份逐轮报告及 `summary.json` 已快照至其 `mixed-feed/` 子目录，避免后续运行覆盖。历史证据仍在 `build/s3-performance-20261013/`。

## vivo 与历史结果的处理

vivo V2361A 新专项目前只有一轮，8 组均采集 180 帧、计数断言通过，证明自动化工作量及子树复用在第二台真机生效，不构成三轮稳定性能结论。其父级优化组 UI p90 为 design_scale 3.973ms、ScreenUtil 4.181ms；局部为 4.225 / 4.275ms，不能据单轮排名。

vivo 历史快速滚动复验中，design_scale 第三轮 total p90 达 26.466ms，187 帧超过 16.667ms；原始批次两库也曾出现 raster 长帧。原因尚未定位。小米新结果和 vivo 专项单轮均不能关闭这个问题，也不能宣称所有真机场景稳定通过。详见 [性能验证](performance-validation.md)。

小米与 vivo 的显示配置、刷新率不同，不能据绝对耗时建立高低端设备排名；iOS 当前只有模拟器功能证据，不提供 iOS 真机性能结论。

## 对外表述边界

适合表述为：实现基于设计坐标的 Flutter 适配方案，支持常量尺寸写法；建立父级重建、局部更新与复杂信息流的自动化对照，在 Android 真机验证静态子树复用及帧耗时，并保留异常轮次以界定适用范围。

如需数字，应同时写出设备、场景、固定更新量和比较对象，例如“在小米 14 的父级更新专项中，每轮 180 次更新，静态详情构建由动态写法的 1440 次降为 0 次；ScreenUtil 合理封装也达到相同构建次数”。不要写成“比 ScreenUtil 快 38%”“全面减少卡顿”或内存、功耗、转化率等未测量的业务收益。

方法、分组和复现命令见 [构建与业务更新专项](update-performance-design.md)。尚未进行分配量/GC、能耗、系统逐帧 trace 或用户体验实验；性能证据不会自动证明接入成本或可维护性优势。
