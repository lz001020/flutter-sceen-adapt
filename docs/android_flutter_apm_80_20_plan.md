# Android + Flutter 性能/APM：二八学习路线

## 目标与时间

针对已有 Flutter Binding/Render/PlatformView 实践、Android 网络埋点和资源治理经历，先投入 **25–40 小时**。每周 10–15 小时，大约 **2–4 周**。这是任务估算，不是能力达成保证；以实验产物验收。

目标：能解释双端线程与帧管线；能判断常见卡顿发生在哪个阶段；能跑通一条跨端 Trace，并验证一次优化。二八原则用于筛选高收益内容，不表示这些内容能保证解决 80% 的线上问题。

此前 3–9 个月的估算包含了 SDK 产品化、兼容、灰度和持续治理。本阶段仅做面向一个真实场景的诊断与采集闭环。

## 优先学习的三件事

| 重点 | 时间预算 | 学习边界 | 验收产物 |
| --- | --- | --- | --- |
| 线程与帧口径 | 5–8 小时 | Dispatcher；Looper/Choreographer/RenderThread/SurfaceFlinger；Dart 事件循环、Isolate；UI/Raster 流水线；实际引擎线程映射 | 一张双端时间线，准确区分等待、同步执行和呈现 |
| 常见卡顿归因 | 10–16 小时 | DevTools 看 UI/Raster 与 CPU；Perfetto 看主线程 running/runnable/blocked，按需看系统呈现证据 | 两组对照实验、一份优化前后报告 |
| 最小跨端链路 | 10–16 小时 | 手动 Span、Channel 上下文传递、局部单调时钟、超时/异常结束、帧指标关联 | 一条 Dart → Android → 任务 → Dart 回调的 Trace |

## 只做一个实验项目

选择已有的图片/Spine 页面或包含原生插件调用的页面。不要另建一整套业务系统。

### 第一段：纠正模型并做对照

1. 在 Dart `await` 后进行明显耗时的同步解析，记录 CPU 与 FrameTiming；移到工作 Isolate，再比较。证明网络等待与 UI 同步解析是两段不同成本，同时计入消息传输开销。
2. 在原生 Channel 处理器中放入受控同步计算，确认实际线程，再卸载到工作线程；用 Perfetto 和往返 Span 比较。证明处理器执行、排队与 UI 回调的边界。

能解释：`async` 不自动切线程；后台任务不直接占用 UI，但可能争抢 CPU/锁；Flutter UI 与 Raster 的耗时不能简单相加判断掉帧。对 Raster/GPU 先掌握如何识别候选方向，遇到真实问题再深入后端。

### 第二段：只串通一条链路

```text
操作根 Span
  → Dart 发起 Channel（传 trace_id、parent_span_id、request_id）
  → Android 处理器 / 工作任务
  → Dart 结果回调同步执行
  → 内容就绪标记 + 关联帧指标
```

最小字段：trace_id、span_id、parent_span_id、阶段名、起止时间、clock_domain、执行端、status。两端在各自单调时钟内算 duration；暂不具备可靠校时时，展示父子关系、因果顺序和局部耗时，不伪造精确的跨端对齐或单向传输时间。

开发环境手动插桩，使用少量结构化记录和现有工具查看即可。无需先做自动 Hook、服务端存储或新大盘。回调只做轻量采集，避免高频同步日志干扰测量；不要将全量调试采集直接发布到生产。

### 第三段：验收一个真实优化

- 能回答：慢在哪里，是线程执行、排队/等待，还是渲染/呈现；每个判断依据是什么。
- 保留固定设备、刷新率、构建模式、操作与数据下的前后轨迹，多轮复测，注明样本数。
- FrameTiming 超预算是阶段线索，不直接当作实际呈现掉帧；下一帧回调也不直接称为 TTI。
- 同一 Trace 在 Channel 两端不丢上下文，成功、异常、超时都有结束记录。

## 暂缓内容与触发条件

| 暂缓内容 | 什么时候再补 |
| --- | --- |
| 全量 Flutter Engine / SurfaceFlinger / 图形后端源码 | 现有证据已定位该阶段，公开指标仍无法解释问题 |
| 自动插桩、全插件覆盖 | 手动链路验证有效，重复接入成本成为实际问题 |
| 跨端高精度校时、复杂 Frame/Span 映射 | 需要定位单向排队或做可靠的统一时间轴 |
| 尾部采样、复杂统计、后台大盘 | 开始生产采集，有明确数据量和查询需求 |
| SDK 全机型兼容、缓存上传、远程熔断 | 准备真实上线时必须安排，不能因二八原则省略 |
| ANR/OOM/泄漏完整专项 | 出现对应业务问题或岗位要求时单独推进 |

完成本阶段后，先用所学处理一个新问题。能够独立迁移方法，再决定是否扩展 SDK；无需先学完整张架构图才开始实际排查。
